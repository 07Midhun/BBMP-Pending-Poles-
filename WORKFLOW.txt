📱 BBMP PENDING POLES — Final Project Summary
1. Project Objective

The mobile application will be used to filter, identify, geographically organize, and locate BBMP pending poles.

The user will select filtering criteria, after which the application will display the matching poles in a clear tabular format.

The poles will be ordered based on their geographical distance from a selected starting pole, rather than by pole number.

11. Geographical Distance Calculation

This is the core ordering requirement.

The application must use the Latitude and Longitude of each pole to calculate its geographical distance from the selected Starting Pole.

The pole number itself must not be used to determine geographical proximity.

For example:

Starting Pole = P0001

P0001 → 12.98204, 77.67365
P0010 → 12.98210, 77.67372
P0100 → 12.98215, 77.67380
P0200 → 12.98300, 77.67500
P0300 → 12.98400, 77.67600

The application calculates the distance from P0001 to every other filtered pole.

12. Distance-Based Ordering

2. What we have already done
A. Backend was created

The Python backend is FastAPI-based and exposes the mobile application's API.

It has APIs for:

GET  /api/v1/regions
GET  /api/v1/zones
GET  /api/v1/wards
GET  /api/v1/pole-with-old-lamp-options
GET  /api/v1/lamp-types
POST /api/v1/poles/filter
POST /api/v1/poles/calculate-distance

There are also ThingsBoard/live-data endpoints.

B. Region → Zone → Ward hierarchy was implemented

We moved toward dependent filtering:

Region selected
    ↓
only zones for that region

Zone selected
    ↓
only wards for that region + zone

The backend's zone endpoint filters the pending dataset by region, and the ward endpoint filters by both region and zone.

This is why your screenshot is now successfully getting to:

Region: EAST
Zone: Hebbal
Ward: HEB-W62

So the hierarchy problem is substantially solved.

C. ThingsBoard live integration was added

The backend is no longer supposed to depend on the old static/sample dataset for production filtering.

The current production filtering path calls:

_get_live_pending_records()

and obtains:

Live Pole Survey
        -
Live Lamp Installation
        =
Live Pending Poles

The backend fetches the complete Pole Survey and installed light-point datasets from ThingsBoard.

The live cache has:

TTL = 300 seconds

so it is refreshed every 5 minutes when needed. A force-refresh endpoint also exists:

POST /api/v1/schnell-iot/refresh-live-cache

D. The backend was changed so live failures aren't supposed to silently fall back to sample data

This is important.

The current /poles/filter production path explicitly uses live ThingsBoard data:

results = _get_live_pending_records().copy()

rather than silently using the old sample dataset.

That is the correct direction for the production application.

E. Flutter asynchronous filtering was improved

The Flutter screen already contains a selection-generation mechanism.

For example:

       ↓
request starts
       ↓
User changes something again
       ↓
older request becomes obsolete
       ↓
older response should not overwrite newer selection

This is a good design because your app performs several asynchronous API requests.

The code uses _selectionGeneration, _distanceRequestId, and _lampTypeRequestId to protect against stale responses.

So we shouldn't throw this mechanism away.

The current live classifier is:

Currently the logic is essentially:

No profiles

The problem is that an existing profile containing something like:

Blank

But your application explicitly defines Empty as having:

-
Blank

The /lamp-types API already returns those values for Empty.

This can cause:

    ↓

5. There is another important problem: API errors and empty results aren't clearly separated

The Flutter app has several places where an API failure can ultimately leave the UI with:

_filteredPoles = []

For example, the screen clears these lists while changing selections and also clears them inside error handling.

That means the user can see:

Backend request failed

Those are completely different states.

We need the UI to distinguish:

Loading
Loading pending poles...
Genuine zero results
No pending poles match these filters.
API failure
Unable to load pending poles.
[Retry]

This is particularly important because you said:

We should make repeated selection changes idempotent and reliable, rather than relying on the user trying again.

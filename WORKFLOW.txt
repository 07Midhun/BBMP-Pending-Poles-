📱 BBMP PENDING POLES — Final Project Summary
1. Project Objective

The mobile application will be used to filter, identify, geographically organize, and locate BBMP pending poles.

The user will select filtering criteria, after which the application will display the matching poles in a clear tabular format.

The poles will be ordered based on their geographical distance from a selected starting pole, rather than by pole number.

The main screen will contain:

4. Ward Dropdown
Field: Ward

The Ward dropdown is completely dependent on the selected Zone.

The application must not display wards belonging to other zones.

For example:

East → Ward 45, Ward 46, Ward 47
West → Ward 60, Ward 61, Ward 62

The user then selects the required Ward.

5. Pole With Old Lamp
Field: Pole With Old Lamp

This dropdown contains three classifications:

Pole With Old Lamp ▼

├── LED
├── Non-LED
└── Empty

The selected value determines the available options in the Lamp Type dropdown.

6. Lamp Type — Dynamic Dropdown

The Lamp Type dropdown is dependent on Pole With Old Lamp.

A. When LED is selected

If:

Pole With Old Lamp = LED

then:

Lamp Type ▼

├── LED
├── FLED
├── LED-FLED
└── LED-LED
Important classification

FLED belongs to the LED classification.

Therefore:

Lamp Type	Classification
LED	LED
FLED	LED
LED-FLED	LED
LED-LED	LED

All four values must be treated as LED.

7. Empty Classification

If:

Pole With Old Lamp = Empty

then the Lamp Type dropdown should contain:

Lamp Type ▼

├── -
└── Blank

Here:

- = hyphen value present in the source data
Blank = empty/null lamp type

For the UI, displaying "Blank" or "No Lamp Type" is preferable to showing an invisible empty option.

10. Starting Pole

After the filtering process, the application should provide another dropdown:

Starting Pole

The Starting Pole dropdown should contain only the poles returned by the selected filters.

Example:

Starting Pole ▼

P0001
P0010
P0100
P0200
P0300

The user chooses one pole as the geographical starting point.

For example:

Starting Pole = P0001
11. Geographical Distance Calculation

This is the core ordering requirement.

The application must use the Latitude and Longitude of each pole to calculate its geographical distance from the selected Starting Pole.

The pole number itself must not be used to determine geographical proximity.

For example:

Starting Pole = P0001

P0001 → 12.98204, 77.67365
P0010 → 12.98210, 77.67372
P0100 → 12.98215, 77.67380
P0200 → 12.98300, 77.67500
P0300 → 12.98400, 77.67600

The application calculates the distance from P0001 to every other filtered pole.

12. Distance-Based Ordering

The application will use Option A — Distance from Starting Pole.

Example:

Order	Pole Number	Distance from P0001
1	P0001	0 m
2	P0010	15 m
3	P0100	30 m
4	P0200	75 m
5	P0300	140 m

The final order is:

P0001
↓
P0010
↓
P0100
↓
P0200
↓
P0300

In other words:

The closest pole to the Starting Pole appears first, followed by the next closest pole, continuing from nearest to farthest.

13. Distance Calculation Method

The distance must be calculated using:

Latitude
+
Longitude

A geographical distance formula such as the Haversine formula can be used.

The system should calculate the distance between:

Starting Pole
        ↓
Every filtered pole

Then sort the results in ascending order of distance.

Example
Starting Pole = P0001

P0001 → 0 m
P0010 → 15 m
P0100 → 30 m
P0200 → 75 m
P0300 → 140 m
14. Final Result — Table View

Instead of KPI cards or individual pole cards, the primary result should be a responsive mobile table.

Filtered Pending Poles
#	Pole Number	Distance	Location
1	P0001	0 m	📍 View Map
2	P0010	15 m	📍 View Map
3	P0100	30 m	📍 View Map
4	P0200	75 m	📍 View Map
5	P0300	140 m	📍 View Map

This is the preferred presentation because the user can quickly compare:

Order → Pole → Distance → Location

15. Location / Google Maps

The source data will contain:

Pole Number
Latitude
Longitude

For example:

Pole Number	Latitude	Longitude
P0001	12.98204	77.67365
P0010	12.98210	77.67372
P0100	12.98215	77.67380

The application will use the latitude and longitude to generate the Google Maps location.

The table will display:

📍 View Map

When the user taps it, the corresponding pole's location opens in Google Maps.

There is no requirement to manually store a Google Maps URL if latitude and longitude are already available.

16. Recommended Table Structure

For mobile, I recommend the table to contain only the information that is useful to the field user:

#	Pole Number	Distance	Location
1	P0001	0 m	📍 Map
2	P0010	15 m	📍 Map
3	P0100	30 m	📍 Map

The raw latitude and longitude do not need to be displayed in the main table.

They can remain as underlying data used to open the map.

17. Responsive Mobile Table

Because this is a mobile application, the table should be designed specifically for smaller screens.

Recommended behavior:

Compact column widths
Fixed/sticky table header
Vertical scrolling for large datasets
View Map as a clickable action
Distance displayed as m for smaller distances
Distance displayed as km for larger distances

🎯 Final concept

The application is essentially a BBMP pole filtering + geographical proximity tool:

Select the area → classify the old lamp → filter the poles → select a starting pole → calculate distance from that pole → display the nearest poles first → open any pole directly in Google Maps.

This is now a clean Version 1 functional specification, and any changes you make during implementation can be added to this structure without changing the fundamental workflow.
